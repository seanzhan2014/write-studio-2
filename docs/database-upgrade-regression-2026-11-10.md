# 生成时报 expansion_json 缺列的修复与检测缺口

生产 D1 数据库的 `runtime_schema_version` 为 21，`outlines` 实际没有 `expansion_json`。新增倍率功能时只更新了字段定义和加列函数，没有更新运行时版本及完整性快速检查。已有库满足原检查条件后直接返回，加列函数没有执行，创建生成任务时才暴露缺列。

原有类型检查、lint 和构建不会连接生产数据库，无法验证运行时 SQL 所引用的列。功能及浏览器测试使用新临时库，会完整执行初始化，因此能正常加列。已有升级测试即便写入“当前版本”标记，也缺少风格实验表，另一个检查条件恰好触发完整升级，掩盖了本次问题。发布验证又只确认部署成功，没有检查真实生产库的列。

修复将运行时版本升级为 22，新库建表也包含倍率列，生成设置加列规则集中到 `AI_GENERATE_SETTINGS_COLUMNS`。新增 `schema-match.ts` 从业务表声明建立完整契约，启动时逐表探测并合并为一个批量请求，不读取业务行。即使数据库被提前标记为当前版本，缺列仍会触发升级；升级后再次匹配，完整通过才能写入新版本标记。无法补齐时立即报出缺失项，避免把不完整数据库标为可用。并发 Worker 实例重复加列时，仅在重新查询确认列已经存在后视为成功，其余错误继续抛出。

新增验证先在修复前复现了相同错误，再验证以下路径：

- 本地和云适配器：其余结构完整，仅缺倍率列；分别使用旧版本 21 和当前版本标记，检查修复与原有大纲、正文版本保留。
- 逐个移除生成列声明中的字段，验证快速检查不会误判“已完整”，并确认升级恢复该列。
- 真实 HTTP 服务从上述旧库启动，实际提交、执行本地演示生成，检查倍率、终稿和旧版本均正常保存。
- 两个实例同时加同一列，以及数据库写入真正失败时的错误传播。

专门的数据库匹配测试覆盖 22 张业务表、248 个字段：逐项移除任一表或字段，检查运行时探测拒绝不完整结构；本地和云初始化必须与声明完整匹配。测试执行全部实际初始化和迁移函数，不再用空函数替代业务迁移。保留从旧结构重建、不含用户数据的固定 `tests/fixtures/database-v21.sql`，独立于当前初始化代码，校验从历史版本升级后仍满足全部最新声明；真实 HTTP 生成也使用这一固定旧库。以后新增字段却遗漏旧库升级步骤时，这条测试会失败。

首次生产核验还发现了普通 SQLite 与 D1 的平台差异：将全部 248 个字段合并成一个结果集的探测在 Node 中通过，在 D1 中报 `too many columns in result set`。已通过 Miniflare 的真实 D1 引擎复现，改为逐表探测的批量请求，并加入 `database-d1-match.test.mjs`；不使用普通 SQLite 模拟此项兼容性。升级失败而缺失项为空时也保留底层错误，避免只返回含糊的“结构探测失败”。

发布后需要实际请求生产运行时，再通过 Sites 数据库只读接口确认列已存在、版本已到 22；发布状态成功本身不能替代数据库升级验证。

专项回归命令：`npm run test:db-match`。这些 `.test.mjs` 同时由默认 `npm test` 发现执行。发布验证也应请求生产运行时并读取数据库实际结构，不能只检查部署状态。
